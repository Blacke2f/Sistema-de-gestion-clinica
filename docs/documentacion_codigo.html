Resumen del Sistema

SISGECLIN v2.5 — Sistema de Gestion Clinica

SISGECLIN es una aplicacion web desarrollada con Laravel 13 (PHP 8.2+) que gestiona todos los procesos operativos de una clinica medica. Implementa el patron MVC con autenticacion por sesiones, control de acceso por roles y permisos granulares por modulo.

Arquitectura MVC

Como esta organizado el codigo del sistema

SISGECLIN sigue el patron Modelo-Vista-Controlador (MVC) de Laravel. Cada capa tiene una responsabilidad clara y separada.

Modelos — app/Models/

Representan las tablas de la base de datos. Definen relaciones, accessors, scopes de busqueda y logica de negocio del dato.

  • Usuario.php — usuarios del sistema + permisos
  • Paciente.php — pacientes de la clinica
  • Consulta.php — consultas medicas
  • Medicamento.php — catalogo de medicamentos
  • Empleado.php — nomina del personal
  • InventarioMovimiento.php — entradas y salidas
  • SolicitudInventario.php — solicitudes de reposicion
  • Mensaje.php — mensajeria interna
  • Notificacion.php — notificaciones del sistema
  • Bitacora.php — auditoria de acciones
  • PermisoUsuario.php — permisos granulares ACL

Controladores — app/Http/Controllers/

Reciben las peticiones HTTP, llaman a los modelos, aplican logica de negocio y retornan vistas o JSON.

  • AuthController — login, logout, registro
  • DashboardController — estadisticas y resumen
  • PacientesController — CRUD pacientes
  • ConsultasController — CRUD consultas
  • MedicinaController — CRUD medicamentos
  • InventarioMovimientosController — entradas/salidas
  • SolicitudesInventarioController — solicitudes
  • NominaController — CRUD empleados
  • UsuariosController — CRUD usuarios + permisos
  • MensajesController — mensajeria
  • NotificacionesController — notificaciones
  • BitacoraController — auditoria
  • PerfilController — perfil y contrasena
  • ExportController — exportaciones PDF/Excel/CSV

Vistas — resources/views/

Plantillas Blade de Laravel. Heredan del layout principal y usan componentes parciales reutilizables.

  • layouts/app.blade.php — layout principal
  • partials/pagination.blade.php — paginador
  • partials/export-modal.blade.php — modal exportar
  • auth/ — login y registro
  • pacientes/, consultas/, medicina/ — modulos
  • inventario/, solicitudes/, nomina/ — modulos
  • usuarios/, mensajes/, bitacora/ — modulos
  • exports/ — templates PDF para mPDF

Middleware — app/Http/Middleware/

Interceptan las peticiones HTTP antes de llegar al controlador para verificar autenticacion, roles y permisos.

  • CheckRole — verifica el rol del usuario (admin, medico, recepcionista)
  • CheckPermiso — verifica permisos granulares por modulo y accion
  • Authenticate (Laravel) — verifica que haya sesion activa
  • RedirectIfAuthenticated — redirige si ya esta logueado

Flujo de una Peticion HTTP

Que pasa desde que el usuario hace click hasta que ve la respuesta

Cada accion del usuario (click en boton, envio de formulario, carga de pagina) genera una peticion HTTP que recorre el siguiente camino:

1

Navegador → public/index.php

El servidor web (Apache/XAMPP) redirige todas las peticiones a public/index.php gracias al .htaccess. Este archivo arranca el framework Laravel.

2

Router — routes/web.php

Laravel busca la ruta que coincide con la URL y el metodo HTTP (GET, POST, PUT, DELETE). Si no encuentra ninguna, retorna 404.

3

Middleware Pipeline

Antes de llegar al controlador, la peticion pasa por los middleware asignados a esa ruta: auth (verifica sesion), role:admin (verifica rol), permiso:modulo,accion (verifica permiso granular). Si alguno falla, retorna error o redirige.

4

Controlador — metodo especifico

El metodo del controlador recibe el objeto Request con todos los datos de la peticion. Valida los datos, llama a los modelos Eloquent y prepara la respuesta.

5

Modelo Eloquent — consulta a MySQL

El modelo traduce las operaciones PHP a SQL y ejecuta las consultas en la base de datos sisgeclin_laravel. Retorna colecciones o instancias de modelos.

6

Respuesta — Vista Blade o JSON

Para peticiones normales (GET de paginas): el controlador retorna view('modulo.index', $datos) que Blade compila a HTML. Para peticiones AJAX (formularios modales): retorna response()->json(['success' => true, ...]).

7

JavaScript — manejo de respuesta AJAX

El script.js recibe el JSON, muestra el toast de exito/error, cierra el modal y recarga la tabla de datos sin recargar toda la pagina.

Ejemplo: Registrar un paciente

// 1. Usuario llena el modal y hace click en "Guardar" // 2. script.js intercepta el submit y hace fetch() a POST /pacientes // 3. Middleware 'auth' verifica sesion activa // 4. Middleware 'permiso:pacientes,crear' verifica que puede crear // 5. PacientesController::store() valida los datos // 6. Paciente::create($data) inserta en MySQL // 7. Notificacion::notificarTodos() inserta notificaciones para todos // 8. Retorna JSON { success: true, message: "Paciente registrado..." } // 9. script.js muestra toast verde y cierra el modal

Autenticacion

Como funciona el login, logout y registro — AuthController.php

El sistema usa autenticacion por sesion de Laravel. No usa tokens JWT ni API keys — todo se maneja con la sesion del servidor y cookies de sesion en el navegador.

Rutas de autenticacion

GET
/login

Muestra el formulario de inicio de sesion. Si ya hay sesion activa, redirige al dashboard.

POST
/login

Procesa las credenciales. Verifica usuario, cuenta activa y contrasena bcrypt.

GET
/register

Muestra el formulario de registro publico (solo medico o recepcionista).

POST
/register

Crea la cuenta con activo=false. Notifica a todos los admins.

POST
/logout

Cierra sesion, invalida la sesion actual y regenera el token CSRF.

Flujo de login paso a paso

1

Validacion de campos

Verifica que username y password no esten vacios. Si faltan, retorna al formulario con errores.

2

Buscar usuario en BD

Usuario::where('username', $request->username)->first() — si no existe, error "Usuario no encontrado".

3

Verificar cuenta activa

Si $usuario->activo === false, bloquea el acceso con mensaje de cuenta desactivada.

4

Verificar contrasena

Hash::check($request->password, $usuario->password) compara el texto plano con el hash bcrypt almacenado.

5

Iniciar sesion

Auth::login($usuario, $remember) crea la sesion. $request->session()->regenerate() previene session fixation.

6

Registrar en bitacora

Bitacora::registrar($userId, 'INICIO SESION', 'usuarios', $userId) guarda el evento con IP y timestamp.

Registro de nuevos usuarios

Los usuarios registrados desde el formulario publico quedan con activo = false. El administrador debe activarlos manualmente desde el modulo de Usuarios. Esto previene accesos no autorizados.
// AuthController::register() — fragmento clave $usuario = Usuario::create([ 'nombre_completo' => $request->nombre_completo, 'username' => $request->username, 'password' => Hash::make($request->password), // bcrypt 'activo' => false, // DESHABILITADO hasta que admin active ]); // Notificar a todos los admins activos $admins = Usuario::where('rol', 'admin')->where('activo', true)->get(); foreach ($admins as $admin) { Notificacion::notificarUsuario(usuarioId: $admin->id, tipo: 'registro_pendiente', ...); }

Sistema de Permisos Granulares (ACL)

Como funciona el control de acceso por modulo y accion

SISGECLIN implementa un sistema de Control de Acceso basado en Listas (ACL). Ademas del rol general (admin/medico/recepcionista), cada usuario tiene permisos individuales por modulo.

Tabla permisos_usuario

CampoTipoDescripcion
usuario_idFKUsuario al que aplica el permiso
moduloVARCHARNombre del modulo: pacientes, consultas, medicina, inventario, nomina, mensajes, usuarios, bitacora, solicitudes
puede_verBOOLEANPuede acceder a la lista del modulo
puede_crearBOOLEANPuede crear nuevos registros
puede_editarBOOLEANPuede modificar registros existentes
puede_eliminarBOOLEANPuede eliminar registros

Middleware CheckPermiso

El middleware permiso:modulo,accion se ejecuta antes de cada ruta protegida. Verifica si el usuario tiene el permiso requerido.

// Ejemplo de ruta protegida en routes/web.php Route::post('/', [PacientesController::class, 'store']) ->middleware('permiso:pacientes,crear'); // CheckPermiso::handle() — logica interna public function handle($request, $next, $modulo, $accion) { $usuario = Auth::user(); // Los admins siempre tienen acceso total if ($usuario->isAdmin()) return $next($request); // Verificar permiso especifico del usuario if (! $usuario->puedeEn($modulo, $accion)) { if ($request->expectsJson()) { return response()->json(['success' => false, 'message' => 'Sin permiso para esta accion.'], 403); } return back()->with('error', 'Sin permiso para esta accion.'); } return $next($request); }

Metodo puedeEn() en el modelo Usuario

// Usuario::puedeEn($modulo, $accion) — verifica permiso public function puedeEn(string $modulo, string $accion): bool { // Admin siempre puede todo if ($this->rol === 'admin') return true; // Buscar el registro de permiso para este usuario y modulo $permiso = $this->permisos()->where('modulo', $modulo)->first(); if (! $permiso) return false; // sin registro = sin acceso // Mapear la accion al campo correspondiente return match($accion) { 'ver' => (bool) $permiso->puede_ver, 'crear' => (bool) $permiso->puede_crear, 'editar' => (bool) $permiso->puede_editar, 'eliminar' => (bool) $permiso->puede_eliminar, default => false, }; }

Sidebar dinamico

El menu lateral del layout principal verifica los permisos antes de mostrar cada enlace. Si el usuario no tiene permiso de ver en un modulo, ese enlace no aparece en el sidebar.

{{-- layouts/app.blade.php — ejemplo de enlace condicional --}} @if(auth()->user()->isAdmin() || auth()->user()->puedeEn('pacientes','ver')) <a href="{{ route('pacientes.index') }}">Pacientes</a> @endif

Modulo Solicitudes de Inventario

SolicitudesInventarioController.php — Tabla: solicitudes_inventario + solicitud_items

Permite a cualquier usuario solicitar la reposicion de medicamentos. Soporta multiples medicamentos por solicitud. Al aprobar, el sistema registra automaticamente la entrada al inventario.

Numero de orden automatico

// Formato: SOL-AAAAMM-XXXX (ej: SOL-202601-0001) // Se genera automaticamente al crear la solicitud $ultimo = SolicitudInventario::whereYear('created_at', now()->year) ->whereMonth('created_at', now()->month) ->count(); $numero = 'SOL-' . now()->format('Ym') . '-' . str_pad($ultimo + 1, 4, '0', STR_PAD_LEFT);

Flujo de una solicitud

1

Verificacion de stock

Al abrir el modal, el sistema verifica si el stock de los medicamentos seleccionados esta por encima del minimo. Si esta bien, muestra aviso "El stock aun tiene medicamentos, desea realizar la solicitud de todas formas?"

2

Creacion de la solicitud

Se crea el registro en solicitudes_inventario con estado pendiente y los items en solicitud_items. Se genera el numero de orden automaticamente.

3

Notificacion a admins

Se notifica a todos los administradores activos para que revisen y aprueben la solicitud.

4

Aprobacion por el admin

El admin hace click en "Aprobar". El sistema cambia el estado a aprobada y registra automaticamente una entrada al inventario por cada item de la solicitud.

Estados de una solicitud

EstadoDescripcion
pendienteSolicitud creada, esperando revision del admin
aprobadaAprobada — entrada registrada automaticamente en inventario
rechazadaRechazada por el administrador
completadaProceso completado y cerrado

Metodos estaticos del modelo

// Notificacion.php — notificar a todos los usuarios activos public static function notificarTodos( string $tipo, string $titulo, string $mensaje, string $icono = 'bx-bell', string $color = 'primary', string $url = '/', ?int $excluirId = null ): void { $usuarios = Usuario::where('activo', true) ->when($excluirId, fn($q) => $q->where('id', '!=', $excluirId)) ->pluck('id'); // INSERT masivo — una sola query para todos los usuarios $data = $usuarios->map(fn($id) => [ 'usuario_id' => $id, 'tipo' => $tipo, 'titulo' => $titulo, 'mensaje' => $mensaje, 'icono' => $icono, 'color' => $color, 'url' => $url, 'leida' => false, 'created_at' => now(), ])->toArray(); Notificacion::insert($data); // una sola query INSERT masivo } // Polling en el navbar — se ejecuta cada 30 segundos // GET /notificaciones/count → { count: 5 } // El badge del campanita se actualiza con el numero retornado

Ruta: GET /buscar — Tiempo real con debounce de 280ms

La barra de busqueda en el navbar realiza busquedas en tiempo real mientras el usuario escribe. Usa debounce para no hacer una peticion por cada tecla presionada.

// layouts/app.blade.php — busqueda con debounce let searchTimeout; searchInput.addEventListener('input', function() { clearTimeout(searchTimeout); searchTimeout = setTimeout(async () => { const q = this.value.trim(); if (q.length < 2) { /* ocultar dropdown */ return; } const res = await fetch(`/SISGECLIN/public/buscar?q=${encodeURIComponent(q)}`); const { results } = await res.json(); // Renderizar resultados en el dropdown dropdown.innerHTML = results.map(r => ` <a href="${r.url}" class="search-result-item"> <i class="bx bx-${r.icon}" style="color:${r.color}"></i> <div><strong>${r.texto}</strong><small>${r.sub}</small></div> <span class="badge">${r.tipo}</span> </a>`).join(''); }, 280); // debounce: espera 280ms despues de la ultima tecla });
